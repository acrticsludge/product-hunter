# Wave 2: Opportunity Investigation Engine

**Status:** specified. The code in `src/product_hunter/research/investigation/` is the
source of truth for every behaviour below. Where this document and the code disagree,
the code wins.
**Date:** 2026-10-21
**Lane:** backend research infrastructure. No UI, so no `DESIGN.md` is required.
**Supersedes nothing.** Wave 1 (`src/product_hunter/research/`) stays the contract,
provenance, budget and gate substrate. This wave builds the investigation pipeline on
top of it and does not change Wave 1 behaviour.

---

## 1. What this wave delivers

The investigator's job is to try to kill a promising idea. This wave makes that
attempt a thing code can check, rather than a thing an agent is asked to do.

It delivers:

- mandatory query families generated by code, so the query set never depends on the
  model inventing it
- a coverage rule that decides when "nothing found" is a real answer and when it is
  the absence of an answer
- structured claims that carry supporting evidence, contradicting evidence, a status
  and a provenance record
- competitor analysis that reports confidence, pricing, positioning, overlap, gaps
  and unknowns
- a startup-killer pass over ten falsification dimensions
- investigation budgets, checkpoints, resume and idempotency
- an opportunity transition that stops at `HUMAN_REVIEW`

Nothing here calls a live tool. The pipeline drives a `ResearchExecutor` protocol, so
the search backend is injected and every rule below is testable without a network.

## 2. Non-goals

| Not in this wave | Why |
|---|---|
| A live search or fetch backend | The rules have to be right before they are wired to a network. The executor protocol is the seam. |
| Market sizing arithmetic | The spec asks for an uncertainty-bounded range from cited evidence. Inventing a number is worse than reporting `unknown`, so this wave reports coverage and unknown, not a number. |
| Opportunity scoring and confidence scoring | Wave 1's contract already routes `scoring` to a separate stage. This wave produces the evidence the scorer reads. |
| A SQLite migration | No new table is needed to hold the investigation record. The record is a value the pipeline returns; persistence arrives with the wave that stores it. |
| Source adapters and URL admission | `config/sources.yaml` and the source adapters own that. The executor is the caller of those adapters. |
| Model routing for the new stages | `config/model_routing.yaml` already names `investigation`, `competitor_research` and `counter_evidence`. This wave does not add a role. |

## 3. The rules this wave enforces

These are the whole point of the wave. Each one is a code rule with a test.

1. **The query set comes from code.** The competitor and counter-evidence families are
   generated by the package, not by the model. A caller may add families; it may not
   remove the mandatory ones, and it may not drop the areas that carry them: the
   competitor and counter-evidence areas are the areas the mandatory families live
   in. The plan holds no duplicate search: every planned query text is distinct.
2. **"Nothing found" is not the same as "nothing exists".** A zero-result conclusion
   is only reachable when the required families were attempted, every attempt
   succeeded, the document coverage floor was met, the distinct-domain floor was met,
   and no tool failed. Anything else reads `INCOMPLETE`. The run's own coverage
   binds the conclusion as well as the areas' does, so a run whose floor it does
   not clear is `incomplete` however complete its areas are.
3. **A conclusion needs its evidence.** A claim with no supporting evidence cannot be
   `supported`, and a claim whose evidence is not in its provenance cannot be
   `supported` either. Evidence that counts for nothing is not evidence: a supporting
   set whose total weight is zero derives `unknown`. A result that says `supported` on
   an incomplete coverage is refused at construction, and so is a recommended state
   the pipeline's own function does not choose for the outcome.
4. **Contradiction is visible.** A claim with contradicting evidence and no recorded
   reconciliation cannot be `supported`. A reconciliation has to name the
   contradiction it addresses: the text must hold the `ref` of a contradicting
   evidence item, and a placeholder such as `n/a` names nothing, so it does not
   reconcile.
5. **A failed search is not a zero.** One failed tool call makes the whole coverage
   incomplete, even when the same family also succeeded on a retry.
6. **Competitors are never assumed absent.** "No competitor found" carries a
   confidence, a coverage record and a list of unknowns. It is a claim, not a fact.
7. **The opportunity is never auto-validated.** The machine path stops at
   `HUMAN_REVIEW`. Only an explicit human decision reaches `VALIDATED`.
8. **The startup killer must actually try.** A dimension reads `survived` only when
   its falsification attempts ran and the coverage was complete, and the coverage it
   has to clear is the run's: a dimension that read one document from one source has
   not survived anything. The assessment records the bar it was judged against, so
   the record and the pipeline agree.
9. **Research resumes, it does not restart.** A checkpoint holds the completed steps
   with the evidence they produced, including the results the calls classified, and a
   resumed investigation re-runs only the steps that are missing and reaches the same
   conclusion. A checkpoint of another problem, another investigation or another run
   is refused. The checkpoint is bounded: the run holds at most a thousand items
   across its steps, and a step that would push it past that is refused like an
   over-cap call.
10. **The payment tier is the classifier's judgement.** The executor reads the tier
    from the evidence; the code only compares the tiers and refuses one outside the
    willingness-to-pay area.
11. **Nothing the executor hands over is stored with a secret in it.** The url
    fields and the `evidence_refs` lists of the items it classifies are stored
    without their userinfo, and a url the pipeline cannot read is not stored at
    all.

## 5. Data model

Every model is a pydantic `BaseModel` with `model_config = ConfigDict(extra="forbid")`,
matching the Wave 1 style. Every model is validated at construction: a value that
should not exist raises rather than being stored.

### 5.1 `queries.py`

```text
QueryFamily(str, Enum)
  competitor_alternative        "{problem} alternative"
  competitor_existing_solution  "{problem} existing solution"
  competitor_software           "{problem} software"
  competitor_pricing            "{problem} pricing"
  counter_not_worth             "{problem} not worth"
  counter_complaints            "{problem} complaints"
  counter_workaround            "{problem} workaround"
  area_existing_solution        "{problem} tools that already do this"
  area_alternative              "{problem} what people do instead"
  area_workaround               "{problem} how people work around it"
  market_validation             "{problem} market demand"
  willingness_to_pay            "{problem} pricing willingness to pay"
  distribution                  "{problem} where to find customers"
  killer_problem_existence      one family per falsification dimension
  killer_recurrence
  killer_severity
  killer_independent_population
  killer_willingness_to_pay
  killer_market_size
  killer_competition
  killer_distribution
  killer_buildability
  killer_timing
```

The ten `killer_*` families replace a single umbrella member. The startup killer is
an area, not a family, and a dimension's coverage is judged on its own family, so an
umbrella family would never be searched.

```text
QueryTemplate(BaseModel)
  family: QueryFamily
  template: str          # contains the literal placeholder {problem}
  purpose: str           # why this family is searched
```

```text
Query(BaseModel)
  family: QueryFamily
  text: str              # the rendered query
  template: str
  purpose: str
```

Functions:

```text
competitor_templates() -> tuple[QueryTemplate, ...]
counter_evidence_templates() -> tuple[QueryTemplate, ...]
area_templates(area: ResearchArea) -> tuple[QueryTemplate, ...]
startup_killer_templates() -> tuple[QueryTemplate, ...]
mandatory_templates() -> tuple[QueryTemplate, ...]      # competitor + counter
render(template: QueryTemplate, problem: str) -> Query
build_queries(problem: str, templates) -> list[Query]
```

Rules:

- `competitor_templates()` returns exactly the four competitor families above.
- `counter_evidence_templates()` returns exactly the three counter families above.
- `mandatory_templates()` is the concatenation of the two.
- Every template contains the literal `{problem}` placeholder. A template without it
  is refused at construction.
- `render` refuses an empty or whitespace-only problem. The rendered text has the
  placeholder replaced by the trimmed problem, and the rest of the template is left
  alone.
- `build_queries` returns one `Query` per template, in template order.

The families are the mission's examples verbatim: `{problem} alternative`,
`{problem} existing solution`, `{problem} software`, `{problem} pricing`,
`{problem} not worth`, `{problem} complaints`, `{problem} workaround`. The three
`area_*` families are the `existing_solution`, `alternative` and `workaround`
areas' own queries, so the plan holds no duplicate search.

### 5.2 `coverage.py`

```text
SearchAttempt(BaseModel)
  family: str
  query: str
  status: ToolCallStatus        # wave 1 enum, reused
  document_count: int = 0       # >= 0
  domains: list[str] = []
  tool_call_id: str = ""
  error: str | None = None
```

```text
CoverageRequirements(BaseModel)
  min_queries: int = 6          # distinct successful queries
  min_documents: int = 1        # documents examined
  min_domains: int = 2          # distinct source domains
```

Every floor is positive. A floor of zero is not a floor: it switches the check off
without saying so, which is the wave 1 lesson about a non-positive limit.

The floors bind at two scopes, and section 7 says how. The run's floors are the
request's, and they bind the run as a whole. An area's floor is the run's floor
with the query count replaced by the area's own step count, so an area is complete
when every query it plans ran and the run's document and domain floors are met. A
dimension is judged on the same floors as an area.

```text
ResearchCoverage(BaseModel)
  required_families: list[str]
  attempted_families: list[str]
  completed_families: list[str]
  failed_families: list[str]
  missing_families: list[str]
  distinct_queries: int = 0
  document_count: int = 0
  distinct_domains: list[str]
  tool_failures: int = 0
  status: CoverageStatus        # complete | incomplete
  reasons: list[str]
```

```text
CoverageStatus(str, Enum)
  complete = "complete"
  incomplete = "incomplete"
```

```text
assess_coverage(
    required_families: Sequence[str],
    attempts: Sequence[SearchAttempt],
    requirements: CoverageRequirements,
) -> ResearchCoverage
```

The rule, in order:

1. `attempted_families` is the distinct families of the attempts.
2. `completed_families` is the distinct families with at least one successful attempt.
3. `failed_families` is the distinct families with no successful attempt.
4. `missing_families` is the required families that were never attempted.
5. `tool_failures` counts every attempt whose status is not `success`. A retry that
   succeeded does not clear the failure: the search was flaky, and a flaky search
   cannot support a "nothing exists" conclusion.
6. `distinct_queries` counts the distinct non-empty queries among the successful
   attempts. `document_count` sums `document_count` over the successful attempts.
   `distinct_domains` is the union of the domains of the successful attempts,
   lowercased and trimmed.
7. The coverage is `complete` only when all five hold:
   - every required family was attempted
   - every required family completed
   - `tool_failures == 0`
   - `distinct_queries >= requirements.min_queries`
   - `document_count >= requirements.min_documents` and
     `len(distinct_domains) >= requirements.min_domains`
8. Otherwise the coverage is `incomplete` and `reasons` names what was missing.

`reasons` holds fixed phrases and counts. It never holds a query, a URL or a domain,
because a reason ends up in a persisted violation and a URL can carry a token.

### 5.4 `claims.py`

```text
ClaimStatus(str, Enum)
  supported = "supported"
  contradicted = "contradicted"
  inconclusive = "inconclusive"
  unknown = "unknown"
```

```text
ClaimEvidence(BaseModel)
  ref: str                      # the handle the provenance knows
  summary: str
  source_url: str | None = None
  tool_call_id: str | None = None
  query_family: str | None = None
  weight: float = 1.0           # 0.0 to 1.0
```

```text
InvestigationClaim(ResearchClaim)     # subclass of the wave 1 claim
  status: ClaimStatus = ClaimStatus.unknown
  supporting_evidence: list[ClaimEvidence] = []
  contradicting_evidence: list[ClaimEvidence] = []
  provenance: InvestigationProvenance | None = None
  confidence: float | None = None      # 0.0 to 1.0
  reconciliation: str = ""             # how the contradiction was addressed
```

`ResearchClaim` is the Wave 1 model. The subclass adds the investigation fields and
inherits `claim_id`, `kind`, `statement`, `stage` and `evidence_refs`, so
`evaluate_promotion` reads the claim unchanged.

```text
derive_claim_status(
    supporting: Sequence[ClaimEvidence],
    contradicting: Sequence[ClaimEvidence],
    reconciled: bool,
) -> ClaimStatus
```

```text
  no supporting evidence                      -> unknown
  supporting evidence that counts for nothing -> unknown
  contradicting evidence and not reconciled   -> contradicted
  otherwise                                   -> supported
```

A reconciliation has to name the contradiction it addresses. The reconciliation
text must hold the `ref` of at least one contradicting evidence item. A placeholder
such as `n/a` names nothing, so it does not reconcile, and neither does a
well-written sentence that points at no evidence. The claim stays `contradicted`.

Validation rules on `InvestigationClaim`, all enforced at construction:

1. `status` must equal `derive_claim_status(...)`, with one exception: a derived
   `contradicted` may be softened to `inconclusive`. Nothing else may be softened.
   `supported` can never be asserted against a derived `unknown` or `contradicted`.
2. `status == supported` requires `provenance` to be present and to have evidence.
3. When `provenance` is present, every evidence item's `ref` must be in
   `provenance.known_refs()`. An unresolvable ref is refused.
4. `confidence`, when present, is between 0.0 and 1.0.
5. `evidence_refs` is filled from the supporting evidence when it is left empty, so
   the Wave 1 `claim_evidence_links` predicate sees the claim's evidence.

Rule 1 is the guard the mission asks for. A model that writes "this is a great
startup" produces a claim with no evidence, and the claim cannot be constructed as
`supported`.

```text

  candidate = "CANDIDATE"         # values are the spec's state names

  promising = "PROMISING"

  validated = "VALIDATED"

```

The member names are lower case, matching every other enum in the package. The
values are the spec's uppercase state names, so a persisted state reads the way the
spec writes it. There is one spelling of each state, not an alias: two spellings of
one member is a duplicate value waiting to be read as two states.

```text
InvestigationOutcome(str, Enum)
  supported = "supported"
  contradicted = "contradicted"
  already_solved = "already_solved"
  inconclusive = "inconclusive"
  incomplete = "incomplete"
```

```text
HumanDecision(str, Enum)
  validate = "validate"
  reject = "reject"
  insufficient_evidence = "insufficient_evidence"
  already_solved = "already_solved"
  request_more_research = "request_more_research"
```

```text
next_state_for_outcome(state, outcome) -> OpportunityState
apply_human_decision(state, decision) -> OpportunityState
allowed_transitions(state) -> tuple[OpportunityState, ...]
```

The machine transition table, from the spec's section 23:

```text
CANDIDATE  -> VERIFYING
VERIFYING  -> PROMISING, INSUFFICIENT_EVIDENCE
PROMISING  -> HUMAN_REVIEW, REJECTED, ALREADY_SOLVED, INSUFFICIENT_EVIDENCE, STALE
HUMAN_REVIEW -> VERIFYING, VALIDATED, REJECTED, ALREADY_SOLVED, INSUFFICIENT_EVIDENCE
STALE      -> VERIFYING, RESURRECTED
```

`next_state_for_outcome` maps an outcome to a state:

```text
supported      -> HUMAN_REVIEW
contradicted   -> REJECTED
already_solved -> ALREADY_SOLVED
inconclusive   -> INSUFFICIENT_EVIDENCE
incomplete     -> INSUFFICIENT_EVIDENCE
```

`next_state_for_outcome` never returns `VALIDATED`, for any input. `VALIDATED` is
reachable only through `apply_human_decision(HUMAN_REVIEW, HumanDecision.validate)`.
A transition that is not in the table raises `InvalidTransition`.

The pipeline uses `next_state_for_outcome` when the table allows the move. When
the current state cannot move to the outcome's state at all, the pipeline picks
the first legal state its own fallback ladder names for that outcome, and the
result carries that state. The ladder is not a second transition table: it never
recommends `VALIDATED`, and it only ever names a state the table allows.

### 5.6 `budget.py`

The Wave 1 `BudgetTracker` already enforces per-run, per-stage and per-source limits
and refuses a call that would break a hard limit. This module does not reimplement
any of that. It scopes the tracker by the investigation stage, so the contract's
per-stage limit for the investigation binds against the investigation as a whole,
and it keeps the investigation's own per-area caps.

```text
InvestigationBudget(BaseModel)          # not a pydantic model: a plain class
  __init__(self, tracker: BudgetTracker, per_area: dict[str, dict[str, float]] | None = None, *, stage: str = "investigation")
  check(self, area, dimension, quantity) -> BudgetDecision
  guard(self, area, dimension, quantity) -> None
  record(self, area, dimension, quantity) -> None
  spent(self, area, dimension) -> float
  exceeded(self) -> list[str]
```

`area` is a `ResearchArea`. The tracker has one stage scope per call, so the scopes
are kept apart: the tracker is scoped by the investigation stage (the contract's
`per_stage.investigation` and the `per_run` limit), and the per-area caps are this
module's own ledger. The run total is recorded once, because the tracker's run
ledger is keyed by dimension alone and recording the same spend under two scopes
would double-count it. A per-area cap of zero or less is refused: a cap that is
not positive would switch the dimension off, which is the Wave 1 NaN lesson applied
to zero.

There is no helper that merges the per-area caps into a `BudgetSpec`. The tracker
is scoped by the investigation stage, so such a spec's per-area entries would never
be consulted: a helper that silently enforces nothing is worse than no helper.
The live mechanism is `InvestigationBudget(tracker, per_area=...)`.

```text
CompetitorAnalysisStatus(str, Enum)
  competitors_found = "competitors_found"
  no_competitors_found = "no_competitors_found"
  unknown = "unknown"
```

```text
CompetitorAnalysis(BaseModel)
  status: CompetitorAnalysisStatus
  competitors: list[Competitor]
  confidence: CompetitorConfidence
  coverage: ResearchCoverage
  unknowns: list[str]
  notes: str = ""
```

```text
analyse_competitors(
    competitors: Sequence[Competitor],
    coverage: ResearchCoverage,
    required_families: Sequence[str],
) -> CompetitorAnalysis
```

The rule:

- competitors found: the status is `competitors_found`, the confidence is the highest
  confidence among the competitors, and the unknowns are the union of the competitors'
  unknowns plus whatever the coverage could not answer.
- no competitors found: the status is `no_competitors_found` only when the coverage is
  `complete`. The confidence is then `medium` at best, because a complete search of a
  narrow slice is not proof of absence. The unknowns list says so.
- otherwise: the status is `unknown`. The confidence is `unknown`.

`no_competitors_found` is never returned with a coverage that is `incomplete`. That
is the mission's "no competitor found does not mean no competitor exists" rule in
code.

```text
  w1 = "W1"   # strong complaint with no payment signal
  w2 = "W2"   # costly workaround, meaningful time or money already spent
```

```text
AreaFinding(BaseModel)
  finding_id: str
  area: ResearchArea
  summary: str
  detail: str = ""
  source_url: str | None = None
  source_domain: str | None = None
  tool_call_id: str | None = None
  query_family: str | None = None
  evidence_refs: list[str] = []

```

The tier is the classifier's judgement: the executor reads it from the evidence
and the finding carries it. A finding with a tier outside the willingness-to-pay
area is refused. The area's tier is the strongest tier among its findings, and
there is no tier when the classifier read none.

A finding's `source_url` and its `evidence_refs` are stored without their
userinfo, because a url can carry a password and a ref can be a url. A url the
pipeline cannot read is not stored.

```text
AreaResearch(BaseModel)
  area: ResearchArea
  findings: list[AreaFinding]
  coverage: ResearchCoverage
  complete: bool
  wtp_tier: WtpTier | None = None
  reasons: list[str]
```

`AreaResearch.complete` is true only when the area's coverage is complete. An area
with no findings and a complete coverage is complete and empty: the research ran and
found nothing, which is a finding in itself. An area with findings and an incomplete
coverage is `complete: false`, because the findings are only part of the picture.

The `wtp_tier` is only meaningful for the `willingness_to_pay` area. It is refused
on any other area.

### 5.10 `startup_killer.py`

```text
FalsificationDimension(str, Enum)   # the mission's ten dimensions, one for one
  problem_existence, recurrence, severity, independent_population,
  willingness_to_pay, market_size, competition, distribution, buildability, timing
```

```text
DimensionStatus(str, Enum)
  survived = "survived"          # the attempt to kill it did not succeed
  falsified = "falsified"        # the dimension was disproved
  inconclusive = "inconclusive"  # too little coverage to decide
```

```text
DimensionAssessment(BaseModel)
  dimension: FalsificationDimension
  status: DimensionStatus
  attempts: list[SearchAttempt] = []
  evidence_refs: list[str] = []
  reason: str = ""
  requirements: CoverageRequirements = ...   # the bar it was judged against
```

The assessment records the bar it was judged against, so the record and the
pipeline agree by construction. The default is one query, one document and two
distinct domains, the same distinct-domain floor the areas use; the pipeline
passes the run's own requirements.

Rules on an assessment:

- `survived` requires at least one attempt and a complete coverage for that
  dimension's families. A dimension nobody attacked has not survived anything.
- `falsified` requires at least one attempt. The reason names the disproof.
- `inconclusive` is the fallback.
- a dimension with no query family is refused, so a dimension that nothing
  searches cannot be reported as survived.

The pipeline judges a dimension on the run's floors, the same ones the areas
clear: a dimension that read one document from one source has not survived
anything.

```text
StartupKillerVerdict(str, Enum)
  survived = "survived"
  falsified = "falsified"
  inconclusive = "inconclusive"
```

```text
StartupKillerReport(BaseModel)
  verdict: StartupKillerVerdict
  assessments: list[DimensionAssessment]
  dimensions_covered: int
  dimensions_required: int
  reasons: list[str]
```

The verdict:

- any dimension `falsified` gives `falsified`
- otherwise any dimension `inconclusive` gives `inconclusive`
- otherwise `survived`, and only when every one of the ten dimensions is present and
  `survived`. A report that covers eight of ten dimensions is `inconclusive`, not
  `survived`.

The report has no `validated` verdict and no way to produce one. It reports whether
the idea survived the attempt.

### 5.11 `checkpoint.py`

```text
  running = "running"

  failed = "failed"
```

```text
InvestigationStep(BaseModel)
  step_id: str
  area: ResearchArea
  family: str
```

A step holds what its call produced, including the results the call classified.
Without them a resumed investigation would find nothing and publish an absence

the checkpoint.

```text
InvestigationCheckpoint(BaseModel)

  run_id: str
```

```text

input_hash_for(query: str) -> str              # sha256, 16 hex characters
build_checkpoint(investigation_id, run_id, problem, steps, contract_fingerprint) -> InvestigationCheckpoint
```

`build_checkpoint` also takes the keyword-only `created_at`, `expected_problem_hash`,

caller says what the checkpoint has to be: a checkpoint of another problem, another
investigation or another run is refused, because it is not a resume of this one and
its evidence would be published under another run's provenance.

`apply_step` replaces the step with the same `step_id` and returns a new checkpoint.
Applying the same step twice yields the same checkpoint, which is what makes the
investigation idempotent. The checkpoint never mutates in place.

`pending_steps` returns the plan steps that the checkpoint does not hold as
`completed`. A checkpoint whose `problem_hash` does not match the request's problem
is refused by `build_checkpoint`, because a checkpoint from a different problem is
not a resume of this one.

### 5.12 `pipeline.py`

```text
SearchOutcome(BaseModel)
  query: str
  family: str
  status: ToolCallStatus
  result_count: int = 0
  documents: list[str] = []          # source urls
  competitors: list[Competitor] = []
  counter_evidence: list[CounterEvidenceItem] = []
  findings: list[AreaFinding] = []
  tool_call_id: str = ""
  error: str | None = None
```

```text
class ResearchExecutor(Protocol)
  def search(self, query: str, *, family: str) -> SearchOutcome: ...
```

The executor is the seam. It searches and classifies in one call, because in
production the same agent does both, and splitting it would add a round trip for no
gain. The rules below never trust it: the pipeline counts what came back and applies
the coverage rule regardless of what the executor says.

```text
PlanStep(BaseModel)
  step_id: str
  area: ResearchArea
  family: str
  query: str
  purpose: str

InvestigationPlan(BaseModel)
  request_id: str
  problem: str
  steps: list[PlanStep]

InvestigationRequest(BaseModel)
  investigation_id: str
  run_id: str
  problem: str
  current_state: OpportunityState = OpportunityState.promising
  areas: list[ResearchArea] = [...]         # every area except startup_killer
  competitor_families: list[QueryFamily] = [...]   # the four mandatory ones
  counter_families: list[QueryFamily] = [...]       # the three mandatory ones
  requirements: CoverageRequirements = CoverageRequirements()

InvestigationResult(BaseModel)
  investigation_id: str
  run_id: str
  problem: str
  started_at: datetime          # timezone-aware, from the injected clock
  finished_at: datetime         # timezone-aware, from the injected clock
  outcome: InvestigationOutcome
  current_state: OpportunityState
  recommended_state: OpportunityState
  coverage: ResearchCoverage
  competitors: CompetitorAnalysis
  counter_evidence: CounterEvidenceResult
  areas: dict[str, AreaResearch]
  killer: StartupKillerReport
  claims: list[InvestigationClaim]
  provenance: InvestigationProvenance
  steps_completed: int
  steps_total: int
  incomplete_reasons: list[str]
  checkpoint: InvestigationCheckpoint   # the state a resumed run starts from
```

The request is refused at construction when it drops a mandatory query family, or
when it drops the `competitor` or the `counter_evidence` area: those areas are
where the mandatory families live, so dropping one of them would drop the
families with it, and the run would end `supported` without having searched them.
A caller may narrow the other areas.

The result is refused at construction when it says `supported` on an incomplete
coverage, when it recommends a state the pipeline's own function does not choose
for the outcome, and when it recommends `VALIDATED`. The check is the pipeline's
own function and not the transition table, so it holds in the states where the
table has no move and the pipeline's fallback ladder picks a legal one.

```text
build_plan(request: InvestigationRequest) -> InvestigationPlan
investigate(
    request: InvestigationRequest,
    executor: ResearchExecutor,
    *,
    budget: InvestigationBudget | None = None,
    checkpoint: InvestigationCheckpoint | None = None,
    clock: Callable[[], datetime] = ...,
) -> InvestigationResult
```

`build_plan` produces one `PlanStep` per area, per family, per template, in a fixed
order: competitor, existing solution, alternative, workaround, market validation,
willingness to pay, distribution, counter evidence, then the startup-killer
dimensions. The plan is a pure function of the request, so the same request always
produces the same plan and the same step ids. No two planned searches ask the same
question: the `existing_solution`, `alternative` and `workaround` areas have their
own templates (`{problem} tools that already do this`, `{problem} what people do
instead`, `{problem} how people work around it`) and their own families, so the
mission's seven families stay in the competitor and counter-evidence areas where
they belong.

`investigate` runs these steps:

1. Build the plan. Build a checkpoint when none was given. A checkpoint that is
   given has to belong to this investigation, this run and this problem, or it is
   refused.
2. For each plan step: if the checkpoint holds it as `completed`, reuse it. The
   executor is not called, the attempt is reconstructed from the checkpoint, and
   the results the call classified come back with it, so the resumed run reaches
   the same conclusion the first run reached. Otherwise the budget is checked
   first, and a denied budget stops the run of further calls: the step is marked
   `failed` and the investigation continues to aggregate what it has.
3. Each call produces a `SearchAttempt` and, on success, a `ToolCallProvenance`
   bound to the run and the investigation stage, and the executor's classified
   results. A call that hands over more than the pipeline holds is refused whole:
   the caps and the spend are described below.
4. Aggregate: coverage per area, the competitor analysis, the counter-evidence
   result, the area research, and the startup-killer report.
5. Build the claims.
6. Decide the outcome and the recommended state.

The outcome:

```text
any required area's coverage is incomplete   -> incomplete
the run's own coverage is incomplete         -> incomplete
the startup killer found a falsification      -> contradicted
counter-evidence items were found            -> contradicted
the startup killer is inconclusive           -> inconclusive
otherwise                                    -> supported
```

The run's coverage binds as well as the areas'. The area floors replace the run's
query floor with each area's own step count, so a run whose own floor it does not
clear is `incomplete` however complete its areas are.

The claims the pipeline builds:

| Claim kind | Emitted when | Supporting evidence |
|---|---|---|
| `no_strong_competitor` | the competitor analysis is `no_competitors_found` | the coverage's completed families |
| `no_counter_evidence_found` | the counter-evidence result is `none_found` | the coverage's completed families |
| `competitors_exist` | at least one competitor was found | the competitors' evidence refs |
| `existing_solution_exists` | the existing-solution area is complete and has findings | the area's findings |
| `market_validated` | the market-validation area is complete and has findings | the area's findings |
| `willingness_to_pay` | the WTP area is complete and has findings | the area's findings |
| `distribution_accessible` | the distribution area is complete and has findings | the area's findings |
| `opportunity_exists` | the startup killer survived every dimension | the dimension assessments' evidence |
| one claim per startup-killer dimension | the dimension is `survived` | the dimension's evidence refs |

A claim is never emitted without supporting evidence, so the claim validator never
sees a `supported` claim with no evidence. A claim whose kind would assert absence
(`no_strong_competitor`, `no_counter_evidence_found`) is emitted only when the
coverage behind it is complete. The absence claim carries the confidence of the
analysis that produced it, so a reader does not have to look it up; a claim with no
source of truth for a confidence carries none.

`recommended_state` comes from `next_state_for_outcome`, so it is at most
`HUMAN_REVIEW`. The pipeline never calls `apply_human_decision`.

#### The gate bridge

```text
investigation_stage_execution(result: InvestigationResult) -> StageExecution
```

The bridge turns an investigation's result into the wave 1 `StageExecution` the gate
judges. It is the only writer of a `ZeroResultOutcome` in this wave, which is what
makes the two zero rules consistent by construction: the wave 1 rule accepts a zero
when the required families were searched and no search failed, and the bridge records
a zero only when the investigation's own stricter rule authorised one.

The execution:

- `stage` is `investigation`, and `status` is `succeeded`. The stage ran; what it
  concluded is a separate fact, and a contradicted conclusion is not a failed stage.
- `started_at` and `finished_at` are the result's own timestamps, which the pipeline
  took from the injected clock. Both are timezone-aware.
- `tool_calls` is the result's tool calls, unchanged.
- `artifacts` is decomposed per producing call, so every artifact traces to exactly
  one successful search call of this stage:

```text
per successful call that produced competitors
  candidate_url   item_count = the distinct competitor urls that call produced
  competitors     item_count = the competitors that call produced
per successful call that produced counter-evidence items
  counter_evidence item_count = the items that call produced
per successful call that produced area findings
  alternatives     item_count = the findings that call produced
```

  A call that produced nothing gets no artifact. Each artifact's `stage` is the
  investigation stage, its `produced_by_tool_call_id` names the call that produced it,
  its `artifact_id` is derived from that call id and the kind, and its `ref` is the
  call's own result ref with the kind appended, which keeps the wave 1 result-ref
  shape. The counts come from the items themselves, which the pipeline stamps with
  the call that produced them.

- `zero_result` is recorded only when both of these hold:
  1. the counter-evidence result is `none_found`, and
  2. the run's coverage has no tool failures.

  When it is recorded, `required_query_families` are the counter families the request
  declared and `completed_query_families` are the counter families that completed.
  When it is not, `recorded` is `False` and both family lists are empty, so nothing
  can be read as a zero.

#### The caps, the spend and the stored urls

The pipeline does not trust the executor's volume, and it does not store what it
cannot vouch for.

- **The item cap.** `SearchOutcome.documents`, `.competitors`, `.counter_evidence` and
  `.findings` are accepted up to `MAX_OUTCOME_ITEMS` (1000) each. A call that hands
  over more is refused whole: none of the data is held or used, the attempt is
  recorded as a failure with the fixed phrase `the search returned more items than
  the pipeline holds`, the step is marked `failed`, and the run carries on with the
  next step, because the other areas are still worth researching. The refusal is
  fail-closed: the failed attempt puts a tool failure in the coverage, so the area is
  incomplete and the run's outcome is `incomplete`, and the zero-result rule refuses
  a zero for that run.
- **The url cap.** The provenance keeps at most `MAX_SOURCE_URLS` (5000) distinct
  source urls. Without it the aggregate is bounded only by the number of plan steps.
- **The checkpoint cap.** The checkpoint carries the classified results, so it is
  bounded too: the run holds at most `MAX_CHECKPOINT_ITEMS` (1000) items across
  its steps. A step whose items would push the run past the cap is refused exactly
  like an over-cap call: the data is not held, the attempt fails with the same
  fixed phrase, the step is marked `failed`, and the run carries on. The refusal is
  fail-closed, so the area's coverage carries the failure, the outcome is
  `incomplete` and the zero-result rule refuses a zero.
- **A stored url carries no credentials.** A url is stored with its userinfo
  removed, so a password in a url never reaches the provenance, the checkpoint or
  the result. The same rule covers the items' url fields and their `evidence_refs`
  lists, because a ref can be a url. A url the pipeline cannot read is not stored:
  it might carry a password the pipeline could not strip.
- **The spend is what the call consumed.** After a successful call the pipeline
  records `BudgetDimension.crawl_items` for the number of items the call returned:
  the documents, the competitors, the counter-evidence items and the findings. The
  shipped contract limits `crawl_items` per run (500), so the spend is limited
  today, and a contract that sets a per-stage limit now applies it as well. The
  items are only known after the call, so the spend cannot be pre-checked: the
  pipeline catches the `BudgetExceeded` the record raises, leaves the spend recorded
  (the call already happened) and stops the run there.

#### The budget's scopes

The tracker has one stage scope per call, so the investigation picks the scopes
apart:

- the tracker's scope is the investigation stage, so the contract's
  `per_stage.investigation` limit binds against the investigation as a whole, and
  the `per_run` limit binds across everything;
- the per-area caps are the investigation budget's own, kept per area;
- the run total is recorded once. The tracker's run ledger is keyed by dimension
  alone, so recording the same spend under two scopes would double-count it, and
  the budget records it once, under the investigation stage.

## 7. Shipped baseline

The shipped investigation policy is the module default:

```text
CoverageRequirements(min_queries=6, min_documents=1, min_domains=2)
```

The three floors bind at two scopes, and the difference matters:

- the run's floors are the request's, and they bind the run as a whole: the run's
  coverage has to have six distinct successful queries, a document examined and two
  distinct source domains;
- an area's floor is the run's floor with the query count replaced by the area's
  own step count, so the competitor area is complete when every query it plans ran
  (four of them) and the counter-evidence area when its three ran, and both have to
  meet the run's document and domain floors;
- a dimension is judged on the same floors as an area.

The document and domain floors are starting values, not measured ones. A caller that
wants different floors passes a different `CoverageRequirements`, and a floor above
what the plan can search makes the run `incomplete` rather than a conclusion.

The shipped contract in `config/research_contract.yaml` is not changed by this wave.
The investigation stage already declares `candidate_url`, `competitors`,
`alternatives` and `counter_evidence` outputs, and the wave 1 gate already reads
them.

## 9. Known limits

These are deliberate boundaries, not promises the code makes.

1. **The executor is trusted to classify.** The pipeline counts and checks what comes
   back, but it cannot tell a real competitor from a hallucinated one. The
   classification is the executor's job and the provenance is the audit trail.
2. **The floors are starting values.** `min_documents=1` and `min_domains=2` are
   placeholders for measured numbers, not a claim about what good research costs.
3. **No persistence.** The checkpoint is a value. Storing it in SQLite arrives with
   the wave that owns the migration.
4. **The startup killer is one pass.** A dimension that survived one attempt has not
   survived a second, and the report does not track how many attempts each dimension
   got.
5. **The market-size range is not computed.** The market-validation area reports
   findings and coverage, not a number. The spec's uncertainty-bounded range is
   computed by the scoring stage from cited evidence.
6. **The investigation stage does not pass the `competitor_search` gate yet.** The
   shipped contract's `investigation` stage requires the `search`, `qdrant` and
   `duckdb` tools, and this wave runs only `search`: the executor protocol has one
   method. The stage the gate judges therefore reports `tool_missing` for `qdrant`
   and `duckdb`. It reports `artifact_missing` for the required outputs this wave
   does not produce: `opportunity_score` and `confidence` belong to the scoring
   stage, and the `candidate_url`, `competitors`, `alternatives` and
   `counter_evidence` artifacts exist only when the search found something. The
   `competitor_search` gate also wants ten candidate urls, which no single
   investigation run produces. So the gate does not pass yet. That is the next
   wave's work, not a defect in this one: the gate is doing its job, and the
   investigation stage is not claiming a pass it has not earned. The contract file
   is not changed by this wave.
7. **The executor's volume is capped, not sampled.** A call that hands over more than
   1000 items of one kind is refused whole rather than truncated. The pipeline cannot
   tell a truncated result from a complete one, and a conclusion that rests on the
   part it kept would be a conclusion about data nobody checked. The cap is a
   boundary, not a quality signal: a well-behaved executor never reaches it.
8. **The stored urls are capped and stripped.** The provenance keeps at most 5000
   distinct urls, and every stored url loses its userinfo. A url whose port cannot
   be read keeps its host and path and loses the malformed port. A url the parser
   cannot read at all is not stored: there is no way to be sure such a url carries
   no secret. The host derivation is
   unaffected: it always worked from the parsed host.
9. **The spend is recorded after the call.** The crawl-items spend is what the call
   returned, so it cannot be checked before the call starts. A contract that sets a
   `crawl_items` limit is enforced after the fact: the spend stays recorded and the
   run stops there.
10. **A reconciliation has to name its evidence.** The rule asks the reconciliation
    to hold the `ref` of a contradicting evidence item. A placeholder such as `n/a`
    does not reconcile, and neither does a well-written sentence that points at no
    evidence. The judgement of what a contradiction was addressed by is still a
    human's, and the rule only insists that the resolution names what it resolves.
11. **The floors bind the run, not each area.** The competitor and counter-evidence
    areas are complete when every query they plan ran and the run's document and
    domain floors are met. The run's six-query floor bounds the run as a whole, and
    any plan of seventeen steps or more clears it, so no single area has to clear it.
12. **The checkpoint is bounded, and a refusal is a failure.** The run holds at most
    a thousand items across its steps, and a step that would push it past that is
    refused like an over-cap call: the data is not held and the attempt fails, so
    the run reads `incomplete` rather than publishing a conclusion from the data it
    kept. The cap is a boundary, not a quality signal.
13. **There is no per-area budget spec.** The tracker is scoped by the investigation
    stage, so a `BudgetSpec` whose per-stage entries name an area would never be
    consulted. The live mechanism is `InvestigationBudget(tracker, per_area=...)`.
