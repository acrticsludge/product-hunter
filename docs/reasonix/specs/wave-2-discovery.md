# Wave 2, Session 2: the discovery engine and the query frontier

## What this wave builds

A discovery engine that decides **what** should be searched. The collection
engine decides **how** a source is fetched, and that engine is not part of this
wave. The two never share a code path: discovery proposes a query and a source,
collection runs it.

The engine keeps a **query frontier**: a persistent set of search queries, each
carrying the family it belongs to, the branch it came from, and the yield it
last produced. The frontier expands itself along code-defined families, measures
what each expansion returned, and stops when a deterministic saturation signal
says it has enough. The caller says how many queries it wants; the frontier
says which family they come from. A query the frontier is handed has its
family re-derived from the code that owns it, so a caller cannot put a query in
a family the worker did not assign. A query that names a template must really
be a rendering of that template, so a caller cannot claim a template it did
not render.

## The one rule that shapes the code

**The strategy lives in worker-side code, not in a prompt.**

A language model may propose a query. It may not decide which family that query
belongs to, which family to expand next, when to stop, or how to phrase a
variant. Those are code decisions with names and reasons attached, and they are
reproducible: the same input produces the same frontier every time.

Concretely, this wave ships:

- eight named query families, defined in `discovery/families.py`
- a template per family, so a variant is generated by substituting a slot, not
  by paraphrasing
- a marker table, so a query of unknown origin is classified by matching
  code-defined markers against its text

A model that returns `"invoice reconciliation"` gets the family that the marker
table says it belongs to. It does not get to pick.

## Query families

| Family | What it looks for | Needs a normalized problem |
|---|---|---|
| `problem` | a plain statement of the problem | no |
| `alternative_wording` | the same problem said another way | no |
| `severity` | how much the problem hurts | no |
| `workflow_pain` | the manual step in the workflow | no |
| `workaround` | the spreadsheet, script or hack people use instead | no |
| `existing_solution` | the tool people already pay for or live with | no |
| `competitor` | the products that claim to solve it | **yes** |
| `counter_evidence` | the reasons the problem is not real | **yes** |

The first six are **mandatory**: a frontier that has run the policy's number of
searches in each of them has covered its family obligation. The last two are
**derived**. They cannot
be written from a raw objective, because a competitor query needs to know which
product category to search and a counter-evidence query needs to know which
claim to push against. Both are generated later, from a
`product_hunter.normalization.NormalizedProblem`, using the same code-defined
templates. This is the spec's rule that competitor and counter-evidence
templates are code-generated from normalized problems.

## The record

Every search the frontier runs produces one record. The record is the unit of
accountability: it says what was searched, what came back, and what it cost.

| Field | Meaning |
|---|---|
| `query` | the search text |
| `family` | the family the worker assigned |
| `source` | the source the query was issued against |
| `run` | the research run |
| `timestamp` | when the search finished |
| `result_count` | how many results the search returned |
| `useful_count` | how many of those the collector judged useful |
| `novelty` | the share of results that had not been seen before |
| `duplicate_rate` | the share of results that had been seen before |
| `cost` | the estimated spend of the search |
| `status` | how the search ended |

`status` distinguishes the case the mission calls out. A search that ran and
found nothing is `empty`. A search whose tool broke is `failure`. The two are
never the same value, because the frontier treats them differently: an `empty`
result is evidence about the query, and a `failure` is evidence about the tool.
A broken tool must never read as saturation.

A `partial` search is a third thing: the tool ran and the search counts
towards the coverage of its family, but it is not a successful one. The
research gate refuses a zero-result outcome when any search call in the stage
did not succeed, so a run that holds a partial search records no zero.

## Novelty and duplicates

Novelty is measured by the frontier against the result identities it has already
seen, across the whole run and every run before it. A result that appears in two
queries is a duplicate the second time, and that is what `duplicate_rate`
counts. The frontier is what computes the novelty, and the frontier computing
it is what makes a novelty true. The record checks only its own arithmetic:
`novelty` and `duplicate_rate` always sum to one, except when the search
returned nothing, where both are zero.

Queries themselves are deduplicated twice over, and the check is scoped to the
source. An **exact** duplicate is a query whose normalized text matches one
already in the frontier against the same source, case and punctuation aside. A
**near** duplicate is a query whose token set overlaps an existing one against
the same source by at least the near-duplicate threshold. A near-duplicate
query is refused and recorded as a refusal, not silently dropped, so the
duplicate rate of the frontier is measurable.

The scope is the source, because the query id is `source|text`: the same
wording against the same source is the same search, and the same wording
against another source is another search. A frontier that could hold one query
per wording across every source could never search a second source with a
wording it had already used, and the source coverage would be unreachable.

## Stopping

The frontier stops for one of five deterministic reasons, and it names the
reason it stopped for.

| Signal | Meaning |
|---|---|
| `diminishing_novelty` | consecutive batches returned less novelty than the policy allows |
| `repeated_results` | the share of the run's results that were repeats is over the policy's limit |
| `family_coverage` | every mandatory family has been searched the policy's number of times |
| `budget_exhausted` | the discovery budget will not admit another query |
| `source_coverage` | every admissible source has been searched |

A frontier that is **blocked** is not a saturated frontier. A failed search sets
`blocked`, and a blocked frontier never reports saturation, no matter how many
batches came back empty. A failed search does not count towards family coverage
and does not advance the low-yield counter, because it says nothing about the
query.

## Budgets

The discovery budget counts queries per run, per source and per family, plus
total spend. It is separate from the research contract's budget, and it does not
replace it: when a `product_hunter.research.BudgetTracker` is supplied, the
frontier consults it as well, so the contract's limits still bind. A query that
would exceed a query limit is not started, and the limit holds when the query
is admitted: a query the frontier has admitted and not yet run already counts
against it, so a batch of admissions cannot overrun a limit that only bit after
the queries had run.

The spend is the other limit, and it is measured after the call, because the
cost of a search is not known before the search runs. A search that goes over it
is counted, its spend stays recorded, and the run is reported as over its
limit: the limit is measured from what was spent, the way the research budget
measures it, because the call already happened. The frontier keeps the house
`BudgetExceeded` rather than letting it escape, so a search that was paid for
keeps its record. The verdict carries a `budget_overrun` signal, and the budget
answers that signal from its own recorded totals, so a restored frontier still
reports the overrun.

The budget is a stopping signal as well as a limit. A frontier that cannot spend
any more is saturated for the reason `budget_exhausted`, which is honest: it
stopped because it ran out of room, not because it ran out of things to find.

## Sources and communities

Discovery proposes sources. It does not admit them.

When a search reveals a community, a repository or a domain that the source
registry does not hold, the caller records it as a **source candidate** with
the query that found it. A candidate carries `terms_status` of `unknown` and no
allowed use, and it stays a proposal until a human reviews it and the registry
records the outcome. The frontier's source coverage counts only the sources the
registry already admits, so a flood of candidates cannot make the frontier look
complete.

The frontier spreads its searches over the sources it was given: the source a
variant is rendered for is the one the frontier has admitted the fewest queries
against, so every admissible source can be searched and the source coverage
reason can fire.

This is the same boundary the source registry already enforces for collection:
an available scraper is not an authorized source.

## Determinism

A query id is `q_` plus the first 16 hex characters of the SHA-256 of the
source id and the normalized query text, joined by a pipe. The same query against
the same source is the same id, in this run and in the next one, so a frontier
can refuse to re-issue a query it already ran, and a replay reproduces the ids.

The normalized text is the case-folded query with punctuation dropped and
whitespace collapsed. Normalization happens once, at construction, and the
normalized form is what the id is taken over.

## Persistence

The frontier is persistent, and it uses the tables the repository already has.

- A query execution is a `research_events` row with the event type
  `DISCOVERY_QUERY_EXECUTED` and the whole record in `payload_json`.
- The cost of a search is a `spend_ledger` row. This table exists for spec §22
  and has had no writer until now.
- The frontier state is a `research_checkpoints` row under the stage
  `discovery`, holding the pending queries, the seen results and the counters.

The state is data and data is not proof. A restored pending query passes the
source gate, the family re-derivation, the duplicate check and the budget
again before it is pending again, so a checkpoint cannot smuggle a query past
the gates it never passed.

No migration is added. The migration number `0003` is reserved by
`docs/reasonix/ARCHITECTURE.md` for a future research-gate wave, and seven
parallel wave-2 branches are going to merge into one trunk; taking that number
here would trade a clean merge for a cleaner table.

The cost of that choice is real and worth naming: the numeric fields of a
record live inside a JSON payload, so a query for "every query with novelty
below 0.1" reads the payload rather than an indexed column. The frontier's own
counters answer that question in memory, and the payload answer is only needed
for a report over a finished run.

## Provenance and the research gate

A discovery record converts into a
`product_hunter.research.evidence.ToolCallProvenance`, so the research gate can
read a discovery run without knowing this package exists. The family travels in
the `query_family` field, which is the field the gate's `query_families`
metric already reads, and the query text travels in `query_or_operation`, which
is what the gate's `distinct_queries` metric counts.

A search that ran and found nothing becomes a successful call with a result
count of zero. A query that was refused as a duplicate, or that the budget
would not admit, becomes no call at all, because no tool ran for it.

## What this wave does not build

Clustering, final scoring, Obsidian output, competitor investigation itself, and
scraping infrastructure are all out of scope. The competitor and counter-
evidence families generate queries; nothing here investigates a competitor.
Discovery is also not a search client: it produces queries and reads results
back, and it never calls an HTTP endpoint.

## Assumptions

- The collection engine is a separate wave. This wave assumes a caller hands
  the frontier a list of result identities after a search, and that the caller
  decides what "useful" means.
- The `useful_count` of a record comes from the collector. This wave measures
  novelty, which it can compute itself, and leaves usefulness to the caller that
  owns the judgement.
- The set of admissible sources is given to the frontier as a list of ids. The
  caller obtains it from the source registry, which is what enforces the terms
  rules.
