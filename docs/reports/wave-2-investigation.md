## 2. The rules the code enforces

These are the reason the wave exists. Each one is a code rule with a test.

1. **The query set comes from code.** The four competitor families and the three
   counter-evidence families are generated by the package, verbatim:
   `{problem} alternative`, `{problem} existing solution`, `{problem} software`,
   `{problem} pricing`, `{problem} not worth`, `{problem} complaints`,
   `{problem} workaround`. A caller may add a family; the request is refused at
   construction if it drops a mandatory one. The executor cannot influence the
   query set at all.
2. **A zero needs real coverage.** A "nothing found" conclusion is reachable only
   when every required family was attempted, every required family completed, no
   attempt failed, and the query, document and distinct-domain floors were met.
   A failed attempt makes the coverage incomplete even when the same family
   succeeded on a retry. Everything else reads `incomplete`, which is the
   mission's `UNKNOWN / INCOMPLETE`, never `NO COUNTER-EVIDENCE EXISTS`.
3. **A conclusion needs its evidence.** A claim with no supporting evidence is
   `unknown` and cannot be constructed as `supported`. A claim whose evidence the
   provenance cannot resolve is refused. A claim with contradicting evidence and
   no reconciliation naming that evidence is `contradicted`.
4. **Contradiction stays visible.** The only softening the validator allows is
   `contradicted` to `inconclusive`, which weakens a claim and never strengthens
   one.
5. **A failed search is not a zero.** One failed tool call makes the whole
   coverage incomplete.
6. **Competitors are never assumed absent.** "No competitor found" carries a
   confidence, a coverage record and a list of unknowns. It is a claim.
7. **The opportunity is never auto-validated.** The machine path stops at
   `HUMAN_REVIEW`. Only an explicit human decision reaches `VALIDATED`.
8. **The startup killer must actually try.** A dimension reads `survived` only when
   its falsification attempts ran and cleared the run's own floors, which include
   two distinct domains. A report covering eight of the ten dimensions is
   `inconclusive`, not `survived`.
9. **Research resumes, it does not restart.** The checkpoint holds the completed
   steps and the evidence they found, and a resumed investigation re-runs only the
   steps that are missing.

## 4. What the reviews found

Two adversarial passes, then a confirmation pass.

### 4.1 The two must-fix bugs

Both were real, both were mission-central, and both are closed.

**A resumed investigation lost its evidence and reached the opposite conclusion.**
The checkpoint stored the search attempt but not the classified results, so a
resumed run re-derived everything from nothing. The reviewer proved it with a
twelve-line probe: a run that found a competitor and twenty-three counter-evidence
items came back `contradicted` and `rejected`, and the same request resumed from
its own checkpoint came back `supported` and `human_review`, publishing
`no_strong_competitor` and `no_counter_evidence_found` as supported claims with
zero executor calls. The searches had found things. The pipeline forgot them and
published an absence claim.

The checkpoint's step now carries the competitors, counter-evidence items and
findings its call produced, and the resume branch restores them with the same
stamping the live path uses. The reviewer re-ran the probe and confirmed
`RESUME == FIRST`, including through a JSON round-trip and a partial resume.

The test that should have caught this was vacuous: it used an executor that
returned nothing, so there was nothing to lose. It now uses an executor that
returns a competitor, a counter-evidence item and a finding.

**`request.areas` could drop the counter-evidence area.** The request validator
guarded the mandatory families but not the areas that carry them, so dropping the
`counter_evidence` area dropped the families with it. A run that had never
searched a single mandatory counter-evidence family ended `supported` and
published `opportunity_exists` plus ten per-dimension claims. The same root cause
crashed the pipeline with a `KeyError` when the competitor area was dropped. The
request is now refused at construction, and the `KeyError` went with it.

### 4.2 The hardening pass

Six findings, all closed: unbounded executor-supplied lists (a memory blowup), a
credential surviving in a stored URL, spend that was not proportional to what a
call consumed, a coverage floor of zero that silently switched the check off, an
artifact id that carried executor-supplied characters, and an unbounded
`result_count` that was declined on purpose because no conclusion reads it.

One residual was closed further than instructed. The implementer reported that a
URL with a malformed port still kept its credentials, because rebuilding the URL
without them means reading the port. The fix drops the malformed port and keeps
the host and path, so the credential goes; a URL the parser cannot read at all is
not stored.

### 4.3 The other findings

Eight should-fix and five nice-to-have findings from the first review, then five
should-fix and eight nice from the second. All are closed. The notable ones: a
result now refuses a `supported` outcome on an incomplete coverage; the wave 1
re-export was incomplete and `from product_hunter.research import investigate`
now works; the shipped contract's `per_stage.investigation` budget was inert and
now binds; a checkpoint from another investigation or run is refused; the
item URLs and the `evidence_refs` lists are credential-stripped; the WTP tier
gained a producer; three of the twenty-three planned searches were exact
duplicates and now have their own templates.

The reviewer withdrew one of its own lean claims, agreeing that replacing the
outcome-to-state fallback ladder with "the first allowed transition" would have
recommended `HUMAN_REVIEW` for a contradicted opportunity.

### 4.4 One rule the orchestrator changed

The reconciliation rule was implemented as "a ref or a sentence of four words or
more", which still let `n/a n/a n/a n/a` reconcile a contradiction. The reviewer's
semantic rule was taken instead: the reconciliation must hold the `ref` of a
contradicting evidence item. One dispatch-1 test fixture was updated to name the
ref it reconciles. Its assertion is unchanged.

1 `explicit_zero_outcome` accepts exactly the zeros the investigation authorised.

## 6. Known limitations

These are deliberate boundaries, documented in the spec's section 9.

1. **The executor is trusted to classify.** The pipeline counts and checks what
   comes back, but it cannot tell a real competitor from a hallucinated one. The
   classification is the executor's job and the provenance is the audit trail.
2. **The floors are starting values.** Six queries, one document, two domains.
   They are enforced consistently; they are not measured numbers.
3. **The area floors are the area's own step counts.** The competitor area is
   complete when the four queries it plans all ran, and the six-query floor bounds
   the run as a whole rather than any one area.
4. **The `competitor_search` gate does not pass yet.** The shipped contract's
   `investigation` stage requires the `search`, `qdrant` and `duckdb` tools and
   outputs `opportunity_score` and `confidence`. This wave runs `search` only and
   produces no score. The gate therefore reports `tool_missing` for qdrant and
   duckdb and `artifact_missing` for the scoring outputs. That is the next wave's
   work, not a defect here.
5. **A run that found nothing produces no artifacts.** The bridge does not invent
   an artifact for a call that returned nothing, so the zero-result path cannot
   satisfy the contract's `candidate_url` output requirement on its own.
6. **The checkpoint is bounded, not free.** A thousand items across the run, and
   a hundred per call. A resumed run counts the items the checkpoint already holds
   against that bound, so a resume cannot double it.
7. **No persistence.** The checkpoint is a value. Storing it in SQLite arrives
   with the wave that owns the migration.
8. **The startup killer is one pass.** A dimension that survived one attempt has
   not survived a second, and the report does not track how many attempts each
   dimension got.
9. **The market-size range is not computed.** The market-validation area reports
   findings and coverage, not a number. The spec's uncertainty-bounded range is
   computed by the scoring stage from cited evidence.

## 7. What was not checked

- The executor contract itself. There is no real implementation in this wave, so
  every statement about what a search actually did rests on the executor's
  honesty.
- The gate bridge against the full contract for a *passing* run. The
  `explicit_zero_outcome` composition was exercised; `evaluate_stage` was not,
  because the stage cannot pass yet for the reasons in limitation 4.
- Persistence. There is no store, so whether a result survives a round trip
  through one is untested.
- Whether the coverage floors are the right numbers. They were checked for
  consistent enforcement, not for correctness.
- A type checker. The package uses PEP 695 generics, correct at runtime and by
  inspection, but no mypy or pyright run backs that.
- The `qdrant` and `duckdb` requirements of the contract's `investigation` stage.

## 8. Debts

- The `ClaimKind` enum in `research/evidence.py` carries twelve investigation
  kinds that the wave 1 gate does not read. The gate reads `claim.kind.value` and
  checks only `no_strong_competitor` and `no_counter_evidence_found`.
- `build_queries()`, `InvestigationBudget.guard()`, `StepStatus.running`,
  `InvestigationStep.attempt` and `OpportunityState.dead` are exported and
  tested but not called by the package. They are the declared interface for the
  waves that follow.
- `investigation_budget_spec` was deleted during the review rounds: it merged
  the per-area caps into a scope the pipeline no longer consults, so a caller
  using it got no enforcement. The live mechanism is
  `InvestigationBudget(tracker, per_area=...)`.
